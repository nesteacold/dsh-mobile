## 1. Host model

- Two knobs per **session**, each a log event (b): `sandbox/mode` `{mode: SandboxMode}` and `approval/policy`; bundled by `permission/preset` (`NM/dsh-permission-presets/README.md:12,85`). Per-session, survives restart by replay; global part is only the *default for new sessions* (`permission` settings namespace, `defaultPreset`) (b, README.md:62-64; `dsh-sandbox-policy/README.md:55-57,79`).
- `SandboxMode = 'read-only' | 'workspace-write' | 'danger-full-access'` (b, e.g. `dsh-api-session-controller/lib/typert.host.js:3504`). Ordering strictest→widest is defined by the escalation ladder `read-only → workspace-write → danger-full-access` (b, `dsh-sandbox/lib/index.js:69-70`).
- Approval policy values seen: `ask`, `never` (b, presets README.md:38-43; `dsh-base/cordis.patch.yml:262`). Full enum not enumerated here (c: possibly more).
- Presets (user-facing value): default table `workspace-write` = {workspace-write, ask}, `danger-full-access` = {danger-full-access, never}; reserved `auto` = {danger-full-access, ask} + auto-review admission; derived `custom` (not selectable) (b, README.md:34-60). The table is **deployment-configurable**, so preset names carry no intrinsic order (c).
- **Read**: session projection `permissions: { currentValue: string }` (preset key | `auto` | `custom`) — already in the session snapshot/summary schema (b, `dsh-api-session-controller/lib/typert.remote-client.js:115-117`). Key absent ⇒ no permission service composed ⇒ hide control. Selectable options: Remote `permissionPresets/catalog` (process-level; returns presets with their sandbox/approval bundle, c — schema at `dsh-permission-presets/lib/typert.remote-client.js:6-33`, not fully read).
- **Write**: there is **no Remote setter**. Only `catalog` is decorated `@Remote` (b, `dsh-permission-presets/lib/index.js:120`). The DSH web UI switches via the slash command `/permission <preset>` executed on the live session (b, `dsh-client-ui-permission-presets/lib/client.js:986`), which calls in-process `permissionPresets.set(session, name)` (b, `lib/index.js:349-366`). So over the wire, setting = `commands/execute` (or `session/prompt` text starting with `/`).
- Whether `session/list` rows carry `permissions` (vs only `session/follow`/`projections`) — not verified (c).

## 3. Can "lower-only" be enforced safely?

- No Host compare-and-set: `set()` reads `current()` and writes knobs with no expected-value parameter (b, index.js:355-366). `/permission` takes only a name.
- Gateway must: read current (projection), resolve both presets to `{sandbox, approval}` from `catalog`, allow only if requested is ≤ current on **both** knobs (sandbox by ladder rank; approval `ask` stricter than `never`), then issue `commands/execute "/permission <name>"` with a gateway-built string (never phone text).
- Race (c): desktop could raise between read and write; the phone's write then *lowers from the new value* — still a lowering, never a raise beyond what desktop set. A raise by the phone is impossible as long as the gateway only ever sends names it judged stricter than the value it read AND re-reads after write to confirm. The residual risk is lowering *less* than intended — benign. Reverse race (desktop lowered, phone sends a "lower" that is now higher than current) IS a raise: mitigate by re-reading `currentValue` immediately before execute and serializing per-session in the gateway; window remains non-zero (no Host atomic). Optional post-write check: if resulting value is wider than pre-write, report `raced` (cannot undo without raising rights; c).
- `auto` and `custom`: treat `custom` current as incomparable unless knob values are known — refuse; never offer `auto` as a target (it is danger-full-access sandbox).
- Exposing `commands/execute` generically is NOT acceptable; the gateway must call it internally for this one composed command only.

## 4. Proposal (for lead)

- Contract ops: `permission-view` (session → `{currentValue, options:[{id, sandbox, approval, rank, selectableLower:bool}]}`), `permission-lower` (`{sessionId, preset, expectedCurrent}` → receipt `{accepted, reason: 'not-stricter'|'stale'|'unavailable'|'custom-current'|'raced', currentValue}`). `expectedCurrent` lets the gateway refuse `stale` if it changed since the phone viewed.
- Scope: view under existing `sessions:read` (read of session state). Lower: **new never-default scope** `permission:lower` — it is a Host-side state change via the slash-command surface, which no existing scope grants to the companion; keeping it separate lets the owner tick it independently and keeps `commands:execute` closed. (Reusing `sessions:author` is possible but it is default-tickable for authoring; c.)
- Gateway checks: device scope; session addressable (same `allows({kind:'session',id})` rule); preset ∈ catalog, ≠ `auto`/`custom`; rank(requested) strictly < rank(current) on sandbox and ≤ on approval (or the pair strictly stricter); `expectedCurrent === currentValue`; per-session mutex; internally-built `/permission <name>`; re-read and return final value; audit log line without args beyond names.
- Do not add to `COMPANION_ENDPOINTS` raw `commands/execute`; add to `COMPANION_UNSUPPORTED_ENDPOINTS` a note for `permissionPresets/*` setters (none exist) for test anchoring.
- App: session screen header chip showing current mode (icon + label from catalog); tap → sheet listing only stricter options, wider ones shown disabled with "change on desktop"; confirm dialog; hide entirely when projection key absent or scope missing.

## 5. Follow-up resolution (beastcore, 2026-11-12)

Paths: `UP/` = `_upstream/dsh-rc1-extract/dsh/node_modules/@deepseek-ai/` (the installed `app.asar` is not greppable as a directory; extracted rc.1 copy read instead — identity with the installed build not re-hashed, c). Everything below is (b) unless labelled.

1. **Enums.** `APPROVAL_POLICIES = ["ask","never"]` — complete (b, `UP/dsh-user-approval/lib/index.js:37`, `lib/types/index.js:17`); permission state schema also only admits these two (b, `UP/dsh-permission-presets/lib/index.js:70`). Strictness: `ask` stricter than `never` — not a named Host ordering, follows from semantics (`never` = no prompts) (c). `SANDBOX_MODES` = `read-only | workspace-write | danger-full-access` (b, `UP/dsh-sandbox-policy/lib/index.js:26`; state schema `permission-presets/lib/index.js:65-69`); ladder order as §1.
2. **`permissionPresets/catalog` result** = `{ options: [{value, name, description?}], defaultOptions: [same], defaultPreset: string }` (b, `UP/dsh-permission-presets/lib/typert.remote-client.js:7-19`; impl `index.js:251-257`, `optionOf` `:330-342`). **It does NOT expose `{sandbox, approval}`.** A Remote client cannot order presets from catalog. In-process the bundle is available: public field `permissionPresets.presets` (`index.js:177`, Config shape `:139-158`) and `resolve(name) → {sandbox, approval, name, description}` (`:318-322`); `auto` resolves to `{danger-full-access, ask}` (`:59-62`).
3. **Current value.** `session/list` rows carry it: `items[].projections.values.permissions?.currentValue` (b, `UP/dsh-api-session-controller/lib/typert.remote-client.js:692,728-730`); also in `session/control` (`:115`), `session/follow` (`:454`) and `session/projections` (`:1081`, `:1304`). Caveat: list rows may be `kind:'cached'` (persisted cache, header-only listing, `:693`) — not live for detached sessions; key absent ⇒ no permission service. In-process: `permissionPresets.current(session)` (`index.js:296-298`) derives live from the projection state.
4. **`commands/execute`.** Wire params: `agentId` (SessionId string, lookup → agent; scope `{context:'agent', wire:'agentId'}`), `line` (complete slash line), `submittedAttachments` (array, `[]` for plain) (b, `UP/dsh-commands/lib/typert.remote-client.js:64-126`). Session(agent)-scoped; needs a live Agent. Result: `{commandId, result:{kind, text?}}` or `undefined` when syntax/name unresolved (`UP/dsh-commands/lib/index.js:327-351`); `command/run` (with `args`) and `command/done` are appended to the session log (`:334-346`). Line: `/permission <preset>`; handler trims rawInput (`permission-presets/lib/index.js:218-219`). Empty ⇒ success text with current + available (`:220-223`). **Name validated** against `names` (configured keys + `auto` only if registered) ⇒ unknown ⇒ `{kind:'error', text:'unknown preset …'}` (`:224-227`). **`custom` is never in `names`** ⇒ rejected as unknown preset (`:51,244-246,178`). Note result `kind:'error'` is a normal settled result, not an RPC failure — gateway must inspect `result.kind`. Command path sets approval via `ctx.approval.setPolicy(agent, policy)` (`:228-230`).
5. **In-process API.** Yes: cordis service `permissionPresets` (constructor `super(ctx,"permissionPresets")`, `index.js:173`), methods `set(session, name)` (`:349-353`), `current(session)`, `resolve(name)`, `presets`, `names`, `catalog()`. A plugin can `inject: ['permissionPresets']` and call `set(agent.session, name)` without command strings (c: not exercised; gateway runs in the same Host process, so injection should work). `set()` validates (throws on unknown via `resolve`, `:356`), runs `autoAdmit` for `auto` (`:357`). **No expected-value/compare parameter** (`:349-366`). Because `current()` + `set()` are synchronous JS with no await between them, a plugin doing `if (current(s)===expected && stricter(...)) set(s,name)` in one synchronous block is effectively atomic against other in-process writers on the single JS thread (c — relies on cordis/event-loop single threading; no Host guarantee). Differences vs command path: `set()` writes approval via `setApprovalPolicy(session, …)` instead of `ctx.approval.setPolicy(agent, …)` (`:351` vs `:229`) — whether the live agent's in-memory approval policy picks up the log event equally is unverified (c); and no `command/run|done` audit events are logged. Also not a public/stable API surface (A1 boundary: calling a service method is not patching, but it is unversioned internals — c).
