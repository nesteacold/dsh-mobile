# DSH Mobile

A native phone companion for a DeepSeek Harness Host. It is a remote control, not a
second copy of the desktop app: the Host keeps executing, the phone keeps looking at
what the Host is doing and telling it what to do next.

There is no WebView and no embedded JavaScript runtime. The app is React Native +
Expo, and the only native code is a pinned-certificate WebSocket bridge, because the
contract requires TLS pinning and a proof-of-possession handshake that the stock
WebSocket client cannot express.

## What you actually get

- **A session list that is the Host's own list.** Workspace picker, recent sessions,
  status pills, relative times, and — behind one reveal — the sub-agent sessions,
  which on a busy Host can outnumber the real ones by twenty to one.
- **Authoring from the phone** when the device was granted `sessions:author`: create a
  session in a chosen workspace, then open it. Without the grant the action is
  disabled *and says why*; with the grant revoked mid-session it stops working on the
  next request, not on the next reconnect.
- **A conversation you can act in.** Markdown messages, tool rows, approval cards,
  a model row that shows the Host's real model, and a composer that reports delivery
  honestly: sent, refused (with the reason), or not confirmed after the request
  timeout — never a bubble that pretends to be sending forever.
- **Pairing that a person can complete.** The Host shows a challenge code, the phone
  answers with a proof bound to the TLS certificate, an owner approves on the desktop,
  and only then does the phone get a token. Close codes are distinct (403 / 408 / 410 /
  401) so the app can tell a revoked device from an unreachable one.

## What is in this repository

| Path | What it is |
|---|---|
| `apps/mobile-companion/` | The phone app: Expo SDK 58, React Native 0.88, expo-router, FlashList. Screens, state, contract client, native WebSocket module, tests and the e2e harness. |
| `packages/mobile-protocol/` | The versioned wire contract shared by app and gateway: op table, scope table, close codes, pairing-proof helpers. Nothing here imports React Native or Node, so both sides can use it. |
| `plugins/mobile-gateway/` | The Host-side plugin: TLS listener, pairing and device registry, per-device policy, the device protocol server, and the projection layer that decides what a device is allowed to see. |
| `plugins/devices/` | The Devices page plugin the gateway registers with, so the desktop can list and revoke devices. |
| `specs/` | The Spec Kit artifacts for the work: contracts, plans, tasks and the acceptance evidence. |
| `tools/verify-publish.mjs` | Checks that this tree is complete before it is published (see Tests). |

## Requirements

- A DeepSeek Harness Host at `dsh-v0.2.2-rc.1`. The gateway declares `engines.dsh` and
  refuses to load on a Host it was not built for.
- Node 22+ for the gateway and the tests.
- For the app: Expo SDK 58 tooling. A physical device or an emulator is required —
  this app talks to a real socket and renders a real keyboard; a browser preview will
  not tell you the truth.

## Install the gateway

Copy `plugins/mobile-gateway/` and `plugins/devices/` into the profile DSH boots, or
install them as a bundle, then enable the gateway. It listens on `127.0.0.1` only until
you switch the listen address from the Devices page.

```bash
cd plugins/mobile-gateway
npm test          # the suite is hermetic; two runs may overlap safely
```

## Build and run the app

```bash
cd apps/mobile-companion
npm install
npm run typecheck
npm test          # node --test, no test framework dependency
node e2e/check-flows.mjs
npx expo run:android          # or: npx expo run:ios
```

`android/` and `ios/` are generated by `npx expo prebuild` and are not committed: they
contain absolute paths from whoever generated them.

## Pairing the phone

1. The gateway is running and the Host is reachable from the phone (same LAN, or a
   tunnel you trust).
2. Mint a pairing offer on the Host with the scopes you intend to grant. `sessions:read`
   and `prompt:send` are the useful minimum; `sessions:author` is what lets the phone
   create sessions and change models.
3. The phone scans or receives the pairing string, answers the challenge, and waits.
4. Approve the pending device on the desktop. Nothing works before that approval.

`harness:remote` is desktop-only and is silently dropped for a phone; a phone cannot
drive another machine's Host, only this one.

## Scopes

| Scope | What it allows |
|---|---|
| `sessions:read` | List sessions and workspaces, read a conversation, watch events. |
| `prompt:send` | Send an instruction to a session. |
| `approval:respond` | Answer an approval card. |
| `files:read` | Read a file the Host offers. |
| `sessions:author` | Create a session in a workspace, list models, select a model. |

Everything else — creating, renaming or archiving a workspace, forking or renaming a
session, settings, commands, plugins, schedules, goals — is refused for every device,
by name, on both the typed and the bridge path. The UI never renders those controls.

`sessions:author` is never granted by default. A device only gets it if the pairing
offer asked for it and the owner approved it, and revoking it takes effect on the next
request because the policy re-reads the device record every time.

## Reachable from another machine

Nothing listens beyond `127.0.0.1` unless you turn it on, and turning it on means TLS
with a pinned certificate. The phone pins the certificate fingerprint it was given at
pairing time; a certificate that changes under it is a hard failure, not a warning.
We do not ship a public relay, and we do not accept a URL from the network.

## What this does not do

- It does not run DSH on the phone. No PTY, no Node, no Host code, ever.
- It is not a terminal. If you want a shell, this is the wrong app.
- It does not mirror the desktop UI. The phone shows what a phone can usefully show;
  the desktop remains the place where everything is possible.
- It does not push notifications in this version. That needs APNs/FCM credentials and
  a server-side sender, and neither is part of this tree yet.
- It has only been verified on an Android emulator against a real Host. iOS builds
  compile, but no signed iOS build ships here.

## Tests

```bash
node tools/verify-publish.mjs    # this tree is complete: every relative import resolves
cd plugins/mobile-gateway && npm test && npm run test:package && npm run check:protocol
cd packages/mobile-protocol && npm test
cd apps/mobile-companion && npm run typecheck && npm test && node e2e/check-flows.mjs
```

The app suite covers the controller, the contract client, the theme's contrast ratios
(computed, both schemes), and the failure branches that are easy to regress: no scope,
refused create, not connected, refused model list. The e2e harness runs a fake gateway
that speaks the real contract and asserts server-side that nothing was sent when it
should not have been.
